
# How we work on issues here
A short checklist the team follows for every bug report or feature request. It is ordinary
engineering practice; nothing here is specific to this repository.

1. Read the issue twice before touching anything. On the second read, write down in one line
   what the reporter expects to happen and what happens instead.
2. Find the code. Search for the names, messages and file paths the issue mentions, then read
   the surrounding function or class whole rather than the matching line alone.
3. Reproduce before you fix. Run the smallest command that shows the reported behaviour. If the
   issue includes a snippet, run that snippet. A fix for a problem you have not seen is a guess.
4. Make the smallest change that resolves the reported behaviour. Prefer editing the function
   that is wrong over adding a new layer around it. Do not refactor neighbouring code, rename
   things, or reformat files you did not need to touch.
5. Keep the change consistent with the surrounding code: same style, same error types, same
   conventions for arguments and return values as the nearby functions use.
6. Run the tests nearest to the change — the test module for the file you edited, and any test
   whose name matches the feature. Read failures fully; a failing test can be telling you the fix
   is incomplete, or that an existing expectation must change because the issue asks for it.
7. Re-run your reproduction from step 3 and confirm the behaviour is now what the reporter
   expected.
8. Review the whole diff once as if you were the reviewer: every hunk should be explainable by
   the issue. Remove stray prints, debugging files and unrelated edits.
9. Stop when the issue is resolved. Do not add features the issue did not ask for.
