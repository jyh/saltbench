
# Conventions for changes in this repository
Ordinary house rules that apply to any change here. They describe how the team prefers work to
look; they do not tell you how to solve a particular problem.

1. Read the whole issue before starting, and keep its wording in mind while you work so the
   change you make is the change that was asked for and not a neighbouring one.
2. Match the style of the surrounding code: the same naming, indentation, quoting, import order,
   error types and docstring shape as the nearby functions use. Do not reformat lines you did not
   need to change, and do not introduce a new helper where an existing pattern already exists.
3. Keep the change small and local. Prefer editing the function or method that is responsible
   over adding a layer around it, a new module, or a new configuration option. Avoid renaming
   public names, moving code between files, or touching unrelated modules.
4. Preserve public behaviour that the issue does not ask to change: signatures, return types,
   default arguments, exception types and messages, and anything documented.
5. Write comments only where the code is not self-explanatory, in the voice the file already uses.
   Do not leave TODO markers, commented-out code, debugging output or scratch files behind.
6. When a change needs a note in the documentation or a changelog entry, follow the existing
   format in the same directory and keep the wording brief and factual.
7. Do not add dependencies, new tooling, or new configuration files. Do not create commits or
   touch version numbers; releasing is handled separately.
8. Stop when the issue is resolved. Do not add features, refactor neighbouring code, or fix
   unrelated problems you happen to notice; mention them in your final message instead.
