### FVAPPS — brief holds: True

The brief holds on task shape, scoring mechanics, toolchain pins, licence and contamination; I re-read every repo file it cited plus the paper PDF text. Corrections and sharpenings:

1. HF FILE SIZES CONTRADICT THE TIER STORY (new, load-bearing). https://huggingface.co/api/datasets/quinn-dougherty/fvapps?blobs=true (and /tree/main) reports: assured.jsonl 11,686,864 bytes; semiassured.jsonl 11,686,864 bytes; unassured.jsonl 11,686,864 bytes; train.jsonl 11,754,428 bytes; test.jsonl 0 bytes. Three "tier" files of byte-identical size cannot be subsets of 1083 / 2089 / 4715 rows — they are almost certainly the same file uploaded three times (LFS oids are masked behind the gate, so identity is inferred from size, not proven). test.jsonl is EMPTY (size 0, not an LFS pointer). So the brief's unknown (1)/(3) is now sharper: the only usable file is train.jsonl, and the tier must be recovered from the `assurance_level` column, not from the per-tier files. The upload script (https://github.com/quinn-dougherty/fvapps/blob/master/src/scripts/hf.sh) just uploads an `artefacts/fvapps` directory wholesale, and jsonl.py's process_benchmark writes only {"train": ...}, consistent with the tier files being an unplanned artefact.

2. "Baseline on 100 samples": the abstract says 100 but the paper body says "We attempt to solve 101 randomly sampled FVAPPS problems" and Table II totals 101 (Unguarded 69 / Guarded 18 / Guarded-and-Plausible 14; Sonnet successes 41/12/7 = 60 samples with ≥1 solved item, Gemini 28/11/4 = 43) — arXiv PDF 2502.05714v1, Table II. 3. "~4 theorems per sample": the paper's actual statement is "Of the 4715 successful samples, the median number of theorems is four (Figure 4)" (PDF, Sec. II.C). Brief's 406/100 arithmetic is a coincidence, not the source.

4. Loop limits: PDF confirms "Both Sonnet and Gemini ran for a maximum of 25 loops for the defs and a max of 50 loops for each theorem"; the shipped toml has max_iterations = 25 for every model (https://github.com/quinn-dougherty/fvapps/blob/master/src/baselines/baselines_config.toml). Since max_iterations is a per-agent constant and baselines.py calls lean_main with the same model config for defs and theorems, the 50-per-theorem run is not reproducible from the shipped config — the paper's number and the code disagree, as the brief suspected.

5. Human baseline: the brief says the human file has "a completed def and no proofs". Actually https://github.com/quinn-dougherty/fvapps/blob/master/artefacts/human_baselines/train/0023/Spec.lean proves `solve_elections_nonnegative` with `by exact Nat.zero_le _` (the trivial `≥ 0` on Nat), leaves an unfinished `simp`/`induction` attempt on `solve_elections_upper_bound` (no sorry, but visibly incomplete), and leaves 2 sorries (zero_votes, single_zero_vote). journal.txt totals 450 minutes (= 7.5 h, not the paper's 10 h). The paper's "did not make it through any of the proofs" is true only for non-trivial proofs.

6. Scoring — the paper itself documents the leak the brief infers: Fig. 6 caption (PDF): "The red box shows completely spurious results, either bugs or a substitution of a quantified variable with a single value." I.e. the authors' own qualitative pass found accepted "successes" where the theorem statement had been weakened (allowed by the system prompt "You may adjust the existing definitions and theorems", https://github.com/quinn-dougherty/fvapps/blob/master/src/baselines/baselines_config.py). Also confirmed: stopping_condition = custom("sorry" not in stdout) AND returncode == 0 (types.py); the model supplies the WHOLE file including imports; theorems are appended one at a time to the accepted Defs_final.lean (baselines.py). No `#print axioms`, no statement diff, no re-check that the model kept the theorem at all.

7. "Guarded" per PDF footnote 8: "Importantly this means that claude-3-5-sonnet-20241022 was able to solve the problem with our scaffold" — i.e. the curated tier is by construction the Sonnet-solvable-implementation subset.

8. ### FVAPPS

**What it is:** "Proving the Coding Interview: A Benchmark for Formally Verified Code Generation" (Dougherty & Mehta, arXiv 2502.05714, v1 submitted 2025-02-08; ICSE 2025 LLM4Code workshop). Lifts the APPS Python coding-interview benchmark into Lean 4: for each APPS train problem, an LLM (claude-3-5-sonnet-20241022) generated property-based tests in Python, then autoformalized them into Lean theorem statements with `sorry` bodies over a `def ... := sorry` stub. Abstract: "a benchmark of 4715 samples for writing programs and proving their correctness, the largest formal verification benchmark, including 1083 curated and quality controlled samples ... we generalize the unit tests to Lean 4 theorems given without proof (i.e., using Lean's 'sorry' keyword)." Baselines: "On the 406 theorems of 100 randomly selected samples, Sonnet correctly proves 30% and Gemini correctly proves 18%." Repo last pushed 2025-05-15 (talk slides); dataset last modified 2025-02-11; 7 GitHub stars — essentially a frozen one-shot artifact, not a maintained benchmark.

**Task shape:** SPEC IS GIVEN. One task = one APPS problem. Dataset row columns (from src/benchmark/postprocessing/jsonl.py, the script that produced the HF jsonl): `apps_id`, `apps_question` (English APPS statement), `spec` (a Lean 4 file), `units` (unit tests converted from the APPS solution), `sorries` (count of the literal string "sorry" in Spec.lean), `apps_difficulty` (APPS's introductory/interview/competition), `assurance_level` (`unguarded` / `guarded` / `guarded_and_plausible`). The `spec` file (dataset-card example, APPS id 23) contains a docstring with the problem, `def solve_elections (n : Nat) (voters : List (Nat × Nat)) : Nat := sorry`, several `theorem ... := sorry` statements over that def, and `#guard_msgs in #eval` unit-test blocks. Dataset card: "The goal is to remove every `sorry` but still make the Lean executable happy." So the solver must (a) implement the def(s) and (b) prove the LLM-written theorems; it does NOT write theorem statements. Per the paper, the ~4715 samples carry ~4 theorems each (406 theorems in 100 samples). NB: the shipped baseline system prompt says "You may adjust the existing definitions and theorems" — the reference harness does not freeze the statement (see scoring).

**Scoring:** Kernel-checked in the weak sense only: the reference harness (src/baselines/types.py) writes the model's whole file to artefacts/baselines/solve-fvapps/SolveFvapps/Basic.lean and runs `lake build` (5-min timeout); success = `returncode == 0` AND the custom stopping condition in src/scripts/baselines.py: `lambda stdout, returncode: "sorry" not in stdout` — i.e. it relies on Lean's "declaration uses 'sorry'" warning text appearing in build output. There is NO axiom check (`#print axioms` never run), NO check that the theorem statements or the def signatures were left unmodified (the prompt explicitly permits adjusting them), NO hidden tests, and no check that `#guard_msgs` unit tests still pass beyond what `lake build` reports. Theorems are scored one at a time: defs are first filled (max 25 loops), then each theorem is appended to the accepted defs and attempted separately (max 50 loops per the paper; 25 per the toml). The repo's own TODO.md admits: "We might need an LLM judge or something to check if proofs are complete (exit code 0 might not be good enough)". Generation-time QA (paper, Sec. on pipeline): Stage 3 "The lean executable is used to typecheck the theorem statements, ignoring the sorrys but ensuring statements are well-formed"; Stage 4 "guarded" = a Sonnet-translated Lean solution passes the inline unit tests; Stage 5 "plausible" = Lean's Plausible property tester finds no counterexample to each theorem against that solution ("Any theorems that are not 'plausible' at this stage, given our solutions that pass unit tests, are filtered"). The paper concedes "it is nontheless possible that particular theorems are not applicable or vacuous in some form."

**Size:** 4,715 samples total = `unguarded` tier (theorem statements typecheck; df.csv in repo: 4715/5000 APPS-train problems had lean_success=True); 2,089 `guarded` (an LLM Lean implementation passes the unit tests); 1,083 `guarded_and_plausible` (all five stages). ~4 theorems per sample (406 theorems / 100 samples in the baseline). Difficulty is the inherited APPS ternary flag (`apps_difficulty` column); the paper gives no per-difficulty counts. HF repo files: train.jsonl, test.jsonl, assured.jsonl, semiassured.jsonl, unassured.jsonl — the postprocessor only writes a `train` split and the baseline CLI only accepts `--split train`, so what test.jsonl holds is unverified (see unknowns). Baseline evaluated 101 sampled problems only.

However, this kind of solution fails to capture inductive structure that lends itself to proofs"), not on spec-writing. ### CLEVER

**What it is:** CLEVER ("Curated Lean Verified code generation benchmark"; repo expands it as "Code Lean Evaluation for Verified End-to-end Reasoning"), Thakur, Lee, Tsoukalas, Sistla, Zhao, Zetzsche, Durrett, Yue, Chaudhuri (UT Austin / Amazon / Caltech), NeurIPS 2025 Datasets & Benchmarks track; arXiv 2505.13938 (v4 dated 23 Oct 2025). Abstract: "a high-quality, curated benchmark of 161 problems for end-to-end verified code generation in Lean. Each problem consists of (1) the task of generating a specification that matches a held-out ground-truth specification, and (2) the task of generating a Lean implementation that provably satisfies this specification ... All outputs are verified post-hoc using Lean's type checker." Problems are 161 of the 164 HumanEval tasks (22, 137, 162 dropped as unformalizable), each with a human-written NON-COMPUTABLE Lean spec (Prop-valued predicate `problem_spec impl inputs`) designed so the spec cannot be copied into an implementation ("non-computable specs thus act as guardrails"). Headline result: few-shot frontier models plus COPRA solve at most 1/161 end to end (problem 53, add two numbers).

**Task shape:** One problem = one Lean file `src/lean4/human_eval/problem_N.lean` with delimited regions (start_def/end_def): `problem_details` (docstring with Python function_signature, NL docstring, HumanEval test cases), `problem_spec` (human ground-truth non-computable Prop spec), `generated_spec` (signature given, body `sorry`), `spec_isomorphism` theorem statement `∀ impl, (∀ x y, problem_spec impl x y) ↔ (∀ x y, generated_spec impl x y)` with proof `sorry`, `implementation_signature` (Lean signature given, body `sorry`), commented `#test` cases, and `correctness` theorem `problem_spec implementation x y` with proof `sorry` (problem_53 quoted verbatim from the repo). Paper §2: given the NL description ν, the model must produce "(1) a formal Lean specification ψ ... (2) a proof that ψ is semantically equivalent to a hidden ground-truth Lean specification ψ*, (3) a Lean implementation π that matches the function signature, (4) a formal proof establishing that π satisfies ψ*." Two certification goals: Specification certification (steps 1-2) and Implementation certification (steps 3-4); note the implementation is proved against the HUMAN spec ψ*, not the model's ψ, so Task 2 is independent of Task 1. The Python API (`clever_bench`, task.py) exposes four component views — SPEC_GENERATION, SPEC_ISOMORPHISM, IMPL_GENERATION, PROOF_GENERATION — each hiding the appropriate ground-truth fields via `view.hide_params()` (e.g. SPEC_GENERATION hides the formal ground truth, implementation and proofs). So: NL spec always given; Lean signature always given; the Lean ground-truth spec is given for the isomorphism, implementation and correctness-proof stages but hidden for spec generation. Theorem statements are fixed by the benchmark; the solver writes only bodies.

**Scoring:** Kernel-checked via Lean 4 compilation of the assembled file: task.py runs `lake lean temp/{filename}` under a configurable timeout (`asyncio.wait_for(..., timeout_in_ms/1000)`, timeout => all flags False, "Timeout") and returns a `ValidationResult` that "will tell you whether your implementation compiled, and whether the proofs were accepted by Lean (i.e., no `sorry`)" (README). Sorry detection is by grepping the build log for `declaration uses 'sorry'` and mapping line numbers to regions. NOT checked: there is no `#print axioms` / custom-axiom check in task.py (so an `axiom` smuggled into the body is not caught by the reference harness — a hole a scout harness must close); `#test` lines are uncommented for implementation compilation but no separate test pass/fail logic. Paper: "A synthesis attempt is deemed successful only when both the proofs generated in the two stages are fully verified by Lean's type checker"; metric is pass@k-seconds with k=600s wall budget per pipeline (retry each stage until compile or timeout), plus compile@k / prove@k per stage; test cases are "deliberately exclude[d] ... from our core success metric". Success table (Table 1): End-to-End at most 0.621% (1/161) for every configuration; best implementation certification 8.696% (Claude-3.7 + COPRA, 14 problems); spec certification best 1.863%.

**Size:** 161 problems (HF dataset amitayusht/clever: 161 rows, single "train" split, 15 columns: function_signature, docstring, test_cases, problem_spec_nl, problem_spec_formal_ground_truth, problem_spec_formal_generated, isomorphism_theorem, isomorphism_proof, implementation_signature, implementation, test_cases_lean, correctness_theorem, correctness_proof, helper_definitions, helper lemmas). Repo tree shows 164 problem_*.lean files in src/lean4/human_eval (0..163 minus 137, 162 per the tree read; paper says 22, 137, 162 excluded — small discrepancy, unresolved). Plus 6 few-shot `sample_examples/problem_0..5.lean` (paper: 5 problems distinct from HumanEval, with hand-written implementations and some isomorphism/correctness proofs, e.g. a 309-line correctness proof).

**Toolchain:** Native (no container) per the repo: `pip install clever-bench && clever-bench-install`, or from source `cd <lean4-dir> && lake exe cache get && lake build`; `src/lean4/lean-toolchain` = `leanprover/lean4:v4.27.0`; `lake-manifest.json` pins mathlib rev a3a10db0e9d66acbebf76c5e6a135066525ac900 (inputRev v4.27.0), plus batteries, aesop, Qq, proofwidgets v0.0.85, plausible, importGraph, LeanSearchClient, lean4-cli v4.27.0. Commit history: "Bump Lean and Mathlib versions to v4.24.0" (2025-11-21) and "Bump Lean and mathlib versions to v4.27.0" (2026-08-26, i.e. two days ago; version bump 1.6.0 -> 1.7.0), so the pin moves. Each task file `import Imports.AllImports`; check = `lake lean` on a temp file inside the lake project.

**Licence:** Code and dataset: MIT ("MIT License / Copyright (c) 2025 Trishul: Trustworthy Intelligent Systems @ UT Austin"; HF card: "License: MIT"). Paper: arXiv CC BY 4.0. Upstream HumanEval: MIT.

**Fit:** Strong fit on mechanics: fixed theorem statements, kernel-decided, sorry-scanned, Lean 4 + mathlib pinned via lake-manifest, MIT, small (161) so a full sweep is affordable, and near-floor SOTA (<=1/161 end-to-end, <=9% impl certification) leaves headroom for a plain/placebo/salt comparison. Two caveats for a kernel-decides design: (a) the reference checker does not audit axioms, so the scout harness must add `#print axioms` or an axiom grep; (b) the pipeline is two-stage and the paper's metric is wall-clock pass@600s, so the scout should fix its own per-stage budget and decide whether to score Task 2 alone (impl + correctness proof against the human spec) — that stage is a clean "implement and prove" unit and is where a "salt" arm (supplying the Salt-style proof-search/lemma-structuring methodology as context) would plausibly act; Task 1 (spec isomorphism) is an abstract reasoning task with no implementation cues and a natural place to test whether salt context helps or is placebo. Contamination: fully public since May 2025 (arXiv v1), GitHub + HF; all problems derive from HumanEval (public since 2021, heavily memorised). The SOLUTION set is largely NOT public: the HF rows and repo files carry the ground-truth spec and (usually) a reference implementation, but isomorphism proofs are `sorry` everywhere sampled and correctness proofs are `sorry` on most rows (row 0 has a real proof; rows 1, 2 and problem_53 are `sorry`; paper says the authors hand-wrote correctness proofs only for "a small random sample"). So implementations are leaked in the dataset (a solver that has seen HF could recall them) but proofs mostly are not; there is no hidden test set. The 5/6 sample_examples with full proofs are the only public exemplar proofs.

**Unknowns:** (1) Exact count: paper says 161 formalized (drops 22, 137, 162) but the GitHub tree listing reported 164 problem files with 137 and 162 missing — one of the two reads is off by problem_22; verify by cloning. (2) Which rows on HF have real vs `sorry` correctness proofs (only rows 0-2 and problem_53 inspected). (3) The `format_problem_as_lean_with_line_ranges` assembly and whether `lake lean` output is parsed for errors beyond sorry (e.g. `#test` failures) — task.py was read via summarizer, not verbatim. (4) Whether the 2026-08-26 v4.27.0 bump recompiles all problems cleanly (no CI evidence read). (5) HF card's own licence/version note for Lean not stated. (6) No container image is provided; hermeticity must be built by the scout.

### other-lean

**What it is:** Survey of Lean-native CODE benchmarks beyond FVAPPS and CLEVER where the Lean kernel decides correctness of PROGRAMS. Read from primary sources (arXiv, GitHub, HF). Classification: PROGRAM-VERIFICATION (spec + implementation + proof, kernel-decided) — Verina (2025, UC Berkeley, 189 tasks, Lean 4), Vero (Aug 2026, UC Berkeley, 43 multi-module Lean 4 repos / 743 APIs / 2,705 specs, code-and-proof mode), Vericoding benchmark Lean track (Sep 2025, Beneficial AI Foundation, 7,141 Lean specs incl. translations from Verina/CLEVER/DafnyBench/FVAPPS/NumPy; spec given, implement + prove), VeriBench (Stanford, 884 tasks, Python→Lean 4 artifact incl. impl+tests+theorems+proofs; kernel-checked but final score uses an LLM judge for theorem equivalence). PROOF-ONLY over programs (implementation and theorem given, produce the proof — theorem-proving about code, not code generation) — miniCodeProps (2024, CMU, 201 Lean 4 program-property specs), VeriSoftBench (Feb 2026, UT Austin, 500 Lean 4 proof obligations from 23 real repos), FVSpec (May 2026, 9,415 Lean 4 specs with sorry placeholders derived from 2,772 Python property-based tests; proof-completion shape per abstract). NOT LEAN (excluded but named for completeness): VerifyThisBench (154 tasks over Dafny/Why3/VeriFast/VerCors/Frama-C/Verus/CBMC — paper says 'Lean is not included' and distinguishes itself from Verina/Clever), VeriContest (946 LeetCode/Codeforces problems in Rust/Verus, toolchain 'Verus 0.2026.04.10'), DafnyBench (Dafny only; no Lean port found — the Vericoding benchmark's DafnyBench→Lean translations are the closest thing to a 'DafnyBench-style port to Lean').

**Task shape:** Verina: each of 189 tasks gives description.txt, task.json (signature, metadata), task.lean (ground-truth code+spec+proof), test.json and reject_inputs.json; HF columns id, description, lean_code, signature, metadata, tests, reject_inputs, difficulty; ids verina_basic_* / verina_advanced_*. Three sub-tasks and their compositions (code gen, spec gen, proof gen; code+spec, code+proof, spec+proof, all three) — spec may be given or must be written depending on sub-task. Sources: 49 MBPP-DFY-50 (translated from Dafny), 59 CloverBench (LLM-translated then manually verified), 81 student submissions from a verification course (LeetCode / LiveCodeBench origin). Vero: a multi-module Lean 4 project with frozen 'shared data types and helpers, API signatures, and formal specifications'; agent fills slots between '!benchmark @start … @end' markers. Two modes: proof (reference impl given, prove specs) and codeproof (write impls AND proofs). Vericoding Lean track: 'Files which compile, up to some sorry or assume false in the code. The file is decomposed into … the preamble, the spec, the code and the postamble' — spec given, solver writes implementation and proof. VeriBench: 'each agent receives only the Python source and must autonomously generate a structured Lean 4 artifact—implementation, tests, theorems, and proofs' — theorem statements must be WRITTEN by the solver (no spec given), then compared to gold. miniCodeProps: program + property statement given, produce proof. VeriSoftBench: 'Theorem name, statement, and source location' given within its original repo context; produce proof. FVSpec: Lean 4 spec with sorry placeholder derived from a Python PBT; fill the proof.

**Scoring:** Verina: 'we use Lean to automatically check the validity of generated proofs, and proofs containing placeholders (e.g., the sorry tactic) are marked as incorrect'; code scored by running against positive test cases (pass@k; #guard-style unit tests in Lean); specs scored for soundness/completeness against the test suites (positive tests + reject_inputs). No explicit axiom-allowlist statement found in the sources read (unknown). Vero: grader 'overlays only the agent's marker-slot bodies, then compiles with Lake and checks each proof's axioms against an allowlist'; 'Editing a frozen file, or renaming and adding markers, cannot change the score. A proof that leaks sorry or an injected axiom does not count'; plus 'a rule-based detector and an LLM judge screen agent-introduced declarations for mechanisms that can trivialize proofs … including malicious typeclass instances and noncomputable choice combined with @[implemented_by]'; also an audit mode where an agent may formally prove a spec unsatisfiable / reference incorrect. Instance counted fully solved only at full spec coverage. Vericoding Lean: compile + 'cheat detection' scanning for sorry, axioms, and attempts to modify the spec (paper HTML); authors note ~9% of specs too weak and ~15% poor translations among inspected successes. VeriBench: SCSC = geometric mean of five factors — IC1 file typechecks (lake env lean, Lean v4.22.0/Mathlib v4.22.0), IC2 theorems verify without sorry, TE1 theorem–gold semantic equivalence 'computed by a Claude Sonnet 4.6 LLM judge', plus gold-side gates D1, D2. 'Generated proofs are allowed to use sorry, and generated artifacts are scanned for axiom declarations and unsafe escape hatches.' So the kernel gates IC1/IC2 but the headline score is NOT purely kernel-decided. VeriSoftBench: proof wrapped into original file context and compiled; 'the ground-truth proof script should contain no proof holes (e.g., sorry or admit)'; Docker-based `docker exec` compile. miniCodeProps/FVSpec: Lean compile of the proof; policy details not read. VerifyThisBench (non-Lean): 'A task is marked as pass/succeed if no error is returned' by the tool, with manual spec-coherence inspection.

### rust-repo-level

**What it is:** Two off-the-shelf repo-level issue-resolution (SWE-bench-style) benchmarks that contain Rust subsets we did not design. (1) SWE-bench Multilingual (Princeton/SWE-bench team; introduced in the SWE-smith paper arXiv:2504.21798 — "SWE-Bench Multilingual consists of 300 task instances that cover 9 additional programming languages"; HF dataset created 2025-04-29, last modified 2026-08-17). 300 instances, 9 languages, of which 43 are Rust from 7 repos (swebench.com/multilingual.html: "tokio-rs/tokio, uutils/coreutils, nushell/nushell, tokio-rs/axum, burntsushi/ripgrep, sharkdp/bat, and astral-sh/ruff"). (2) Multi-SWE-bench (ByteDance Seed; arXiv:2504.02605, CC BY 4.0 paper; HF dataset created 2025-03-31, last modified 2026-07-08). 1,632 instances across 7 languages; Rust = 239 instances from 10 repos per the paper's Table 1 (ripgrep 14, clap 132, nushell 14, rayon 2, serde 2, bat 10, fd 14, bytes 5, tokio 25, tracing 21) — note clap alone is 55% of the Rust subset. A "mini" variant (ByteDance-Seed/Multi-SWE-bench_mini, 400 instances) has exactly 50 Rust instances across the same 10 repos. A 2026 paper (arXiv:2602.22764, "Rust-SWE-bench", 500 tasks / 34 repos, CC BY 4.0) confirms both counts verbatim ("43 instances from 7 repositories"; "239 instances from 10 repositories") and criticises them as small; its release URL could not be located in this pass.

**Task shape:** One task = a real GitHub issue + a repo snapshot at the pre-fix commit; the solver must produce a code patch (diff) that makes hidden tests pass. No spec or theorem is written — the "spec" is the natural-language issue text plus the test files added by the original PR (held back from the solver, applied at grading time). SWE-bench Multilingual fields (datasets-server /info): base_commit, created_at, eval_type, image, instance_id, log_parser, repo, version, patch, test_patch, eval_script, problem_statement, hints_text, FAIL_TO_PASS, PASS_TO_PASS. `patch` is the gold fix ("The gold/reference fix resolving the issue") and `image` is a per-instance Docker image ref, e.g. "swebench/sweb.eval.x86_64.tokio-rs_1776_tokio-6752:latest". Multi-SWE-bench instances are per-repo JSONL files (rust/ folder: BurntSushi__ripgrep_dataset.jsonl 1.58 MB, clap-rs__clap_dataset.jsonl 28.8 MB, nushell, rayon, serde, bat, fd, bytes, tokio, tracing) with fields including fix_patch ("A fix-file patch that was contributed by the solution PR"), test_patch, p2p_tests/f2p_tests/s2p_tests/n2p_tests, fixed_tests, and a recently added hints field. Submissions are {org, repo, number, fix_patch}. Rust instance dates in Multilingual span 2022-01 to 2025-02 (e.g. tokio-rs__tokio-4384 2022-01-07 … tokio-rs__tokio-7139 2025-02-05; all 7 ruff instances Jan 2025).

**Scoring:** Not kernel-checked — purely test-based. SWE-bench harness (swebench/harness/grading.py): "If fail-to-pass (Resolution) = 1 and pass-to-pass (Maintenance) = 1 -> FULL; If (fail-to-pass < 1 and > 0) and pass-to-pass = 1 -> PARTIAL; Otherwise -> NO"; leaderboards count FULL only. The candidate patch is applied in the instance container, test_patch is applied, eval_script runs, a language log parser (Rust parser present in swebench/harness/log_parsers/) maps test names to PASS/FAIL, and FAIL_TO_PASS / PASS_TO_PASS lists from the dataset are checked. Multi-SWE-bench harness (multi_swe_bench/harness/report.py): runs three phases (run / test / fix) and Report.check() marks valid iff fix-phase captured results ("if self.fix_patch_result.all_count == 0" → invalid), no test goes PASS→FAIL ("test.test == PASS and test.fix == FAIL" → invalid), at least one test goes non-PASS→PASS (populates fixed_tests), and no anomalous patterns; gen_report.py additionally requires every dataset p2p/f2p/s2p/n2p test be present in the report; FinalReport lists resolved_ids vs unresolved_ids. No sorry/axiom concept — hidden tests are the sole oracle, and both harnesses publish the gold patch alongside the tests.

**Size:** SWE-bench Multilingual: 300 total, 43 Rust / 7 repos (counts verified via datasets-server search for 4 of the 7: tokio 9, axum 3, ripgrep 2, ruff 7 = 21; coreutils, nushell, bat searches returned HTTP 500 so the remaining 22 are inferred from the stated 43). Dataset ~1.9 MB download. Multi-SWE-bench: 1,632 total; Rust 239 / 10 repos (paper Table 1); mini = 50 Rust; the full HF repo is ~1.8 GB, rust/ folder ~41 MB. Docker: mswebench/clap-rs_m_clap has a base tag (537 MB compressed) and ≥32 pr-* tags up to 1.87 GB each; scripts/images_verified.txt lists 2,889 image lines of which 287 are Rust (base + pr tags). Multilingual images e.g. tokio-6752 are ~683 MB compressed, linux/amd64 only.

**Toolchain:** No Lean/mathlib or Verus — this is cargo test in Docker. SWE-bench: images are pre-built on Docker Hub under the `swebench` namespace, one per instance, named sweb.eval.x86_64.<org>_1776_<repo>-<pr>:<tag>; the harness pulls whatever string is in the instance's `image` column ("client.images.pull(test_spec.image)") — by TAG, not digest; the dataset pins ":latest", and tokio-6752 shows two tags (v1 digest 09628aed243c, >1 yr old; latest digest 7b323a0d3d8e, pushed 15 days ago by jyangballin) — i.e. the image behind the tag was re-pushed this month, so digest pinning must be done by us at snapshot time. ARM: "Support for arm64 machines is experimental"; use --namespace '' to build locally. Toolchain versions per repo are baked into the images (harness tree carries swebench/harness/constants/fixtures/ with Cargo.lock files, implying pinned lockfiles per Rust repo; exact rustc versions not read). Multi-SWE-bench: harness (Apache-2.0) builds/pulls images named "mswebench/{org}_m_{repo}:{tag}" with tags base or pr-<n>; image.py "Digests are not used anywhere"; scripts/download_images.sh reads images_mini.txt / images_verified.txt / images_rl.txt (tags only, no sha256); if absent locally the harness builds them from Dockerfiles in multi_swe_bench/harness/repos/ (note: the GitHub tree listing seen had no rust/ folder under repos/ — the Rust build recipes' location is an unknown). All Rust images are linux/amd64 and last pushed >1 year ago. Both run natively on Linux Docker; nothing pinned to a Lean or Verus release.

Multi-SWE-bench dataset: "The dataset is licensed under CC0, subject to any intellectual property rights in the dataset owned by Bytedance. The data is adapted from the listed open source projects; your use of that data must comply with their respective licenses." (HF api tag says license:other); harness: "This project is licensed under Apache License 2.0."; paper CC BY 4.0. Underlying repo code: MIT/Apache-2.0/Unlicense (tokio, clap, ripgrep, etc.) — permissive.

**Fit:** Weak fit for a kernel-decided scout. The "kernel" here is cargo test on hidden tests, not a proof checker: there is no theorem statement, no spec, and no proof object — "solved" is a test-status vector, so the placebo/salt arms would be judged by the same fallible test oracle (patches that game or under-specify tests pass). Contamination exposure is total: both datasets ship the gold fix (patch / fix_patch) and the test_patch publicly (Multi-SWE-bench since 2025-03-31, Multilingual since 2025-04-29), the source PRs are merged upstream on GitHub (2022–2025), and the Docker images with the gold state are public — well inside any 2026 model's training window; both leaderboards are heavily reported. What a "salt" arm would do: the only Rust-native lever is to hand the solver, alongside the issue, a derived formal obligation (e.g. a Verus/Kani/proptest harness or the F2P test names as a spec) and grade on test pass PLUS that extra check — but that is our design layered on their substrate, and no arm is decided by a kernel. Useful mainly as (a) a public, permissively licensed pool of realistic Rust repo snapshots (tokio, clap, nushell, ripgrep, coreutils, axum, ruff, bat, fd, tracing, bytes, serde, rayon) with working build containers, from which a salt-style verification task could be cut, and (b) a calibration baseline (SWE-agent + Claude 3.7 Sonnet resolves 43% of Multilingual at $2.50/task). Size is small for Multilingual (43) and lopsided for Multi-SWE-bench (clap = 132/239).

**Unknowns:** (1) Per-repo Rust counts for Multilingual's coreutils/nushell/bat could not be fetched (datasets-server HTTP 500) — the 43 total is from swebench.com and the paper; only 21 were individually confirmed. (2) Exact rustc/cargo versions baked into each image were not read (constants fixtures show Cargo.lock files; docker build code path not located after the harness refactor — test_spec.py/docker_build.py now 404 at their old paths). (3) Whether the `latest` re-push on 2026-08 of the Multilingual images changed anything material vs `v1` (digests differ: 7b323a0d3d8e vs 09628aed243c). (4) Location of Multi-SWE-bench Rust Dockerfiles in the harness tree (repos/ listing showed no rust/ folder in the fetched excerpt). (5) Multi-SWE-bench "verified" vs full: images_verified.txt has 287 Rust lines while the paper says 239 instances — the difference is base tags plus possibly unlisted/extra PRs; not reconciled. (6) Rust-SWE-bench (arXiv:2602.22764, 500 tasks) release URL/HF id not found — worth a dedicated scout if a larger Rust pool is wanted. (7) SWE-bench Multilingual has no standalone paper; construction/validation details beyond the swebench.com page (human validation?) are undocumented in the SWE-smith paper text read.

### verus-proof-native

**What it is:** The family of Verus (verified Rust) benchmarks for LLM proof synthesis, all checked by the Verus verifier itself. Core members read from primary sources: (1) Verus-Bench (AutoVerus, Microsoft, arXiv 2409.13082): 150 algorithm-level "add the proof annotations" tasks; (2) VeruSAGE-Bench (arXiv 2512.18436, Dec 2025): 849 repository-extracted proof tasks from 8-9 real Verus systems (Anvil, IronKV, NRKernel, ATMO/Atmosphere, Vest, ...), both shipped in github.com/microsoft/verus-proof-synthesis; (3) the Vericoding benchmark (Beneficial AI Foundation, arXiv 2509.22908, Sep 2025): 2,334 Verus specs with `sorry`/`assume(false)` holes where the solver must write BOTH implementation and proof (vericoding rather than proof-only); (4) adjacent 2025-26 sets: RVBench (755 repo-level Verus proof-completion tasks, arXiv 2509.25197), VCoT-Bench (1,988 completion tasks derived from Verus-Bench, arXiv 2603.18334, judged partly by LLM), Verus-SpecGym (581 spec-writing tasks from Codeforces, arXiv 2605.26457), VeriContest (competitive-programming Verus, arXiv 2605.08553). SAFE's "VerusBench" is the same 150-task Verus-Bench; the 1,435 figure is SAFE's separate LLM-crafted CodeNet-Test, not VerusBench (arXiv 2410.15756 search summary). Toolchain: Verus is a static verifier for a Rust subset ("Developers write specifications ... Verus statically checks that the executable Rust code will always satisfy the specifications", github.com/verus-lang/verus), driven by rustc front-end + Z3.

**Task shape:** Verus-Bench (proof-only): input is a single unverified .rs file with spec (requires/ensures) AND executable implementation already present; the solver adds proof annotations only (loop invariants, asserts, proof blocks, lemmas). README: "The `task` field contains the unverified code (INPUT)"; `unverified/` and `verified/` (GROUND TRUTH) dirs; tasks.jsonl fields task_id, source, name, task, ground_truth. AutoVerus rules: "Lynette compares the pure Rust AST of the files after erasing the ghost code" (exec code must be unchanged), "compares the pre- and post-condition ... so the LLM cannot tweak them", "searches for debugging ghost function, such as admit() or assume()". VeruSAGE-Bench (proof-only, repo context): each task "a standalone Rust file containing: Dependencies, Context, and Target"; the target function keeps signature+spec, "we manually go through every F_verified.rs file and remove all the proof annotations inside F"; callees are stubbed: "we keep the signature of F', but replace its body with `unimplemented!()` and tag it with `verifier::external_body`". Agent instruction: "You should NOT change existing functions' pre-conditions or post-conditions; you should NOT change any executable Rust code; and you should NEVER use admit(...) or assume(...)". Vericoding (impl+proof): spec given, decomposed into vc-preamble/vc-helpers/vc-spec/vc-code/vc-postamble with `sorry`/`assume false` holes; "Each language folder contains a `tasks` folder with specs which compile, up to some `sorry` or `assume false` in the code"; solver produces code and proof. No task in any of these requires the solver to write the theorem statement/spec (except Verus-SpecGym, whose object IS the spec).

**Scoring:** Solved = the Verus verifier accepts the file. Success line from the Verus guide: "verification results:: 1 verified, 0 errors" (verus-lang.github.io/verus/guide/getting_started_cmd_line.html). Trust base = Z3 (SMT solver; no proof-term kernel, no independent checker), Verus itself (VIR->AIR->SMT encoding, vstd axioms), and rustc (front-end/type checking; Verus pins rust-toolchain.toml channel = "1.97.1"). This is NOT a kernel-checked result in the Lean sense; a trustworthiness argument rests on Z3+Verus soundness plus post-hoc cheat filtering. Cheat policy: Verus-Bench/AutoVerus = Lynette AST diff of exec code + pre/post equality + admit()/assume() scan; VeruSAGE-Bench README: "A task is considered **solved** if Verus verification succeeds and there is no cheating" (no assume/admit, no added external_body, no spec/exec changes; a named public checker script was not found in the README excerpt). Vericoding: prohibited "(1) Using assume(false) or sorry to disable the proof checker. (2) Changing postconditions in the spec to ensures true"; spec fidelity of translations was validated by "LLM as a judge". Reference Verus commits stated in microsoft/verus-proof-synthesis README: AutoVerus 33269ac6a0ea33a08109eefe5016c1fdd0ce9fbd; VeruSAGE ddc66116aa7a844a9e19cc50922fe85c84b8b4a5; VeruSAGE-Bench README: "A Verus version in or after Sep. 2025 is highly recommended." No hidden tests anywhere; ground truth is public. VCoT-Bench scoring is partly an LLM judge (not kernel), so it is unsuitable as a checker-decided arm.

**Size:** Verus-Bench: 150 (CloverBench 11, MBPP-DFY-153 78, Diffy 38, Misc 23). VeruSAGE-Bench: 849 (table: Anvil 104, Anvil Adv 63, IronKV 118, Mem Alloc 89, Node Repl 29, NRKernel 204, ATMO 157, Storage 63, Vest 22; plus a 100-task sampled subset; a no-lemma variant without ground_truth). Vericoding Verus: 2,334 specs (paper Table 2 gives 2,166 after quality checks: APPS 536, NumpyTriple 581, DafnyBench 440, VerifiedCogen 172, HumanEval 161, Verina 156, Bignum 62, NumpySimple 58); whole HF dataset 12,504 rows single train split. RVBench: 755 tasks / 337 modules / 3,464 functions across 4 projects. VCoT-Bench: 1,988. Verus-SpecGym: 581. Solve rates reported: AutoVerus >90% of Verus-Bench (GPT-4 era); VeruSAGE best "over 80%" (Claude Sonnet 4.5, 81%, 7.2 min/task); vericoding Verus 44% off-the-shelf.

**Toolchain:** Verus: MIT (LICENSE: "Copyright (c) 2021 The Verus Contributors"), rolling weekly releases named 0.YYYY.MM.DD.<sha> (latest seen: "Rolling Release 0.2026.08.28.908ebe1", 0.2026.08.23.fbbbbcf, 0.2026.08.15.7d4628a, ...); rust-toolchain.toml pins channel "1.97.1" with components rustc, rust-std, cargo, rustfmt, rustc-dev, llvm-tools; vstd is Verus's verified standard library shipped with the release; prebuilt binaries via INSTALL.md, source builds via BUILD.md. Check = `verus file.rs` on a standalone file (Verus-Bench, VeruSAGE-Bench single-file tasks) — native binary, no container prescribed by any of the benchmarks; Vericoding uses per-language scripts in its repo. Benchmark authors pin Verus by commit (see scoring). Z3 version: fetched by tools/get-z3.sh, but the raw file URL returned 404 so the pinned Z3 version could not be confirmed here.

**Licence:** Verus toolchain: MIT. microsoft/verus-proof-synthesis (Verus-Bench + VeruSAGE-Bench, code and ground truth): MIT, "copyrighted by Microsoft in 2024". Beneficial-AI-Foundation/vericoding and vericoding-benchmark repos: MIT; HF dataset card beneficial-ai-foundation/vericoding: "mit". VCoT-Bench paper: CC BY 4.0 (repo not located). Verus-SpecGym: CC BY 4.0, github.com/formal-verif-is-cool/verus-spec-gym. VeriContest: CC BY 4.0, github.com/HIPREL-Group/VeriContest and HF Gax-c/VeriContest. RVBench licence not checked. Upstream source projects of VeruSAGE-Bench (Anvil, IronKV, etc.) carry their own licences, not verified here.

**Fit:** Verifier-decided arms are feasible: every core set is decided by running `verus` plus a mechanical cheat filter (exec-AST unchanged, pre/post unchanged, no assume/admit/external_body), all reproducible from public MIT code; no LLM judge needed except VCoT-Bench (exclude). Caveat for the scout's "kernel deciding" framing: the decider is Z3+Verus, not a proof kernel — soundness rests on the SMT solver and Verus's encoding; there is no independent re-check, so the harness must at least pin the Verus commit and Z3 and run the cheat filter itself. Contamination: Verus-Bench public since Sep 2024 with all 150 ground-truth proofs in `verified/`, and its sources (MBPP, CloverBench, Diffy) are old public sets — heavily exposed and near-saturated (>90% by AutoVerus in 2024; SAFE 79%). VeruSAGE-Bench public since Dec 2025 with ground_truth in tasks.jsonl; the underlying projects are on GitHub with their proofs except ATMO/Atmosphere ("was not released online until we reached out to the developers in November 2025") — the only near-uncontaminated slice, 157 tasks, and even it is now public with solutions. Vericoding public since Sep 2025 (HF, MIT) with sources drawn from HumanEval/APPS/DafnyBench etc.; solutions partially public in `vericoded`/`handcoded`. Plain arm = spec+impl (or spec only for vericoding) given, agent writes proof under the cheat filter. Placebo arm = the same prompt with an irrelevant method preamble. A "salt" arm here would mean giving the agent the Salt method's proof-discipline scaffolding (decomposition into lemmas, invariant-first drafting, explicit trusted-base bookkeeping) as workflow guidance; the natural Verus analogue is invariant/lemma-first proof planning before touching the file — but Verus proofs are SMT-automated hint-writing, not kernel-level term construction, so the salt intervention is farther from its home than in Lean, and the effect would be diluted by Z3 doing most of the work. Best-fit subset if used: VeruSAGE-Bench ATMO (157) and NRKernel (204) with a fresh Verus pin, treating public ground truth as a known contamination ceiling; Verus-Bench only as a sanity/calibration set.

**Unknowns:** Pinned Z3 version (tools/get-z3.sh returned 404 via raw fetch; not confirmed). Whether microsoft/verus-proof-synthesis ships a named, runnable cheat-checker script for VeruSAGE-Bench (README states the rule, the excerpt shows no script; AutoVerus's Lynette exists in-repo per the paper but was not located here). Leaderboard contents (page linked, not fetched). VeruSAGE-Bench README says "8 real-world Verus projects" while its table lists 9 rows (Anvil and Anvil-Advanced likely one project) — unresolved. RVBench release/licence and Verus pin not checked. VCoT-Bench repository URL not found. Full VeruSAGE cheating-detection rule list and per-project public-release dates beyond ATMO were not read (PDF unparseable; HTML gave partial quotes). Whether the vericoding Verus tasks are pinned to a Verus commit (not stated in README/HF card excerpts). Exact vstd/Verus versions the ground-truth proofs verify under today (rolling releases break older proofs; the README's "in or after Sep. 2025" is a recommendation, not a pin).
